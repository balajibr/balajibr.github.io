Why this was filed Planning a migration was the part nobody had automated. Assessment tools could inventory an estate and map dependencies, but the actual judgment — which applications move together in which wave, when each one cuts over, which databases have to travel with which apps — came out of spreadsheets and architects’ heads. Onix had built a system where an AI model produced that plan from the raw inventory and then validated the wave grouping it proposed, carried it through to a generated landing zone, and kept tuning the environment after the move. This patent claims that planning-to-post-migration loop; its companion, US 12,124,869, claims the execution chain that consumes the plan.

I.Five Modules, One Loop

Claim 1 recites five modules in a chain, each “operatively connected” to the one before it. The chain is not purely linear in effect: the fourth module, the post-migration phase module 118, runs a continuous improvement loop that analyzes each completed phase and feeds corrective actions back into subsequent waves. That loop is what separates this from a one-shot planning tool — the claim requires fine-tuning the loop for later waves, not just reporting on the first one. The fifth module is a chatbot 122, claimed as part of the same system rather than as a separate support product.

Numbering note The specification numbers the chatbot module inconsistently — col. 10 introduces it as “a chatbot module 120” in the same sentence where 120 is the artificial intelligence model, while col. 11 and the claims consistently use 122. This map follows the col. 11 usage: AI model 120, chatbot module 122.

II.Method 400 — Eight Steps

Claims 9 and 18 restate the system as method 400, eight steps numbered 402–416. The distribution is lopsided on purpose: three of the eight steps (410, 412, 414) belong to the post-migration phase module, which is where the claimed value sits. Only one step covers the landing-zone generation that most migration tooling treats as the main event.

III.Companion Filing — Plans Out, Plans In

This patent and US 12,124,869 were filed one week apart by an identical set of seven inventors, and they interlock. The recommendation module 114 here produces a migration wave plan, a cutover plan per application, a database migration plan, security and compliance policy details, and a data migration plan. Those are, almost item for item, exactly what the other patent’s data acquisition module 60 is claimed to acquire as its input. Read together, one patent claims deciding what the migration should be; the other claims carrying it out.

V.How This Differs From Existing Tools

The migration tooling market is crowded, but it is crowded in segments. Discovery and assessment products inventory the estate and map dependencies; portfolio-analysis products score applications for refactoring; landing-zone products provision infrastructure from templates; optimization products right-size instances after the fact. The gap this patent addresses is that no single product ran the whole line — and specifically, none of them produced the migration wave plan itself. That artifact was a human deliverable, assembled from the assessment tools’ exports.

Reading this fairly Two caveats. First, this comparison describes the tool landscape around the April 2024 filing; several of these products have since added AI-assisted planning features, and a like-for-like comparison today would need re-checking. Second, the claim is not that no tool does any of these things — it is that the claimed combination runs them as one chain, with the AI model validating the wave grouping and the post-migration loop feeding subsequent waves. Individual capabilities in the table above were, and are, available separately.
