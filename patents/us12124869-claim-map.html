Field of Invention, col. 1, verbatim

“Embodiments of the present disclosure relate to a field of data migration and more particularly to a system and a method to automate migration of one or more resources to a cloud.”

Background, col. 1, paraphrased

Migration waves are today prepared manually from infrastructure inventories, application logs, database inventories, and compliance reports. The patent characterizes that process as slow, costly, and prone to data-security, accuracy, and compliance failures. The claimed invention automates that wave-planning-through-deployment sequence end to end.

Why this was filed At the time, there was no single tool that carried a migration from wave plan to running application in the cloud. Teams stitched together a landing-zone provisioner, a storage tool, a network tool, a database-migration tool, a server lift-and-shift tool, and an application deployment tool by hand, with an engineer gluing each handoff to the next. Onix had already built a system that did all six stages itself, chaining the output of one stage into the trigger for the next, and set out to patent that specific chain rather than any one stage in isolation. The plans this system consumes as input are themselves the claimed output of a companion filing, US 12,204,505, filed one week earlier by the same seven inventors.

I.Three Claims, One Invention

The patent files the same automation pipeline three separate ways: as a system, as a method, and as a computer-readable medium. This is standard claim drafting: it lets an infringement theory reach whoever builds the system, whoever performs the steps, or whoever distributes the software, without needing three different inventions. All three independent claims recite the identical six-module chain; claims 19 and 20 are close mirrors of claim 1 restated in method and CRM form.

II.The Automation Pipeline: Claim 1

Claim 1’s six modules are claimed in a fixed sequence, each “operatively coupled” to the one before it. What matters legally is not just the module list but the trigger language binding three of the six couplings: storage migration 80 begins upon security details being applied by 70; network configuration 90 begins upon storage being configured by 80; data migration’s dependency analysis begins upon secure communication being established by 90. The other three couplings, data acquisition 60 to landing zone 70, and data migration 100 through server 110 to application migration 120, are claimed only as structural coupling, with no analogous “upon” clause.

III.Method 300: The Same Chain as Seventeen Steps

Claims 19 and 20 restate Fig. 1’s six modules as method 300, a sequence of seventeen numbered steps (310–470) spread across the specification’s Figs. 4a–4c. Collapsed onto one timeline, each module owns a short run of consecutive step numbers: one for data acquisition, three each for landing zone creation, data migration, server migration, and application migration, two each for storage and network configuration. Step 470, deploying the applications, is the step the claim itself calls out as the point “thereby automating the migration.”

IV.Dependent Claims: Scope Narrowing

Claims 2 through 18 all depend on claim 1 and narrow it along independent axes: cloud deployment model, resource type, requirement categories, networking primitives, and, notably, the database technology behind the “integrated database 50.” That last group is deliberate: claiming SQL, NoSQL, and sequential/columnar variants keeps the claim from being read narrowly around one storage technology.

Note on scope Claims 10–18 read as breadth insurance rather than technical distinctions. They don’t change what the system does, only where it runs and what it’s backed by. Their value is defensive: a design-around that swaps SQL for NoSQL, or a local server for a cloud-hosted one, still falls inside claims 16–18 or 10–11 respectively, so it doesn’t avoid the patent by that move alone.
